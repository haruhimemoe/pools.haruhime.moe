# AGENTS.md

Rules for any agent (or human) working in this repo. Authoritative; `CLAUDE.md` only layers on top.

## 1. What this is

pools.haruhime.moe (in beta) is where you build an osu! tournament mappool: any osu! user signs in and makes pools (`built_pools`) with co-editors, a map browser that searches every osu! map under a mod lens, values under each slot's mods, the compliance check and played-before, and each unlisted or public pool with maps gets its own pack on packs.haruhime.moe, kept in step. Past osu! tournament mappools stay as reference, in their own `pools` collection, from three kinds of source (otdb's export through an importer; tournament hosts and community members, whose pools admins add at `/admin/pools/new`), with a plain pack per pool on packs.haruhime.moe and a read-only public side (pool search with a past / built here / both type, a search of every osu! map through the hinai mirror with the ones officially supported tournaments can't use left out, maps played in pools, map history, a compliance check, `/data`, `/submit` and the Discord server for sending pools, "Start from this pool"). Admins moderate built pools and keep the past-pool tools. What users read lives in `README.md`, `/data`, `/submit`, `/credits` and `content/legal/`; section 7 says what has to stay in step with the code.

**Hard rule: we never host files.** No `.osz`, audio, image or video bytes pass through or are stored by our code. Map previews (`MapPreview`, `src/utils/map-preview.ts`) load the set's cover from assets.ppy.sh and its clip from b.ppy.sh in the browser; one clip plays at a time (`src/hooks/usePreviewPlayer.ts`) and stops once no button for its set is left on the page (`holdPreview`); both URLs are built only from a positive whole set id (`isSetId`), and the builders throw for anything else. The CSP in `next.config.ts` allows images from here, `data:` URIs, a.ppy.sh and osu.ppy.sh (avatars, and `osuAvatarSrc` from `@haruhimemoe/next-kit/auth-react` shows none from anywhere else) and assets.ppy.sh, and media from b.ppy.sh only (`tests/unit/config/headers.test.ts`); a new image or media host needs a line there. "Open in packs", "Download on packs" and the mirror link send people elsewhere.

## 3. Code style

- TypeScript 7, `strict`, `noUncheckedIndexedAccess`. No `any`; validate external data with zod.
- Biome is the only linter and formatter (`bun run check`, `bun run check:fix`).
- No barrel files in `src/`. Import exact local paths. npm packages are imported from their published entry points.
- One component per file, PascalCase filename, Tailwind only. Components are presentational; data lives in services and hooks. A component file exports only components and their prop types: copy goes in `src/constants/`, helpers in `src/utils/`.
- Take what the shared packages have instead of copying it: server plumbing from `@haruhimemoe/next-kit` (route helpers, rate limits and the osu! budget, env, MongoDB and its indexes, osu! sign-in, the account store and the account components), wired once in `src/lib/api.ts`, `rate-limit.ts`, `osu.ts`, `db.ts`, `db-indexes.ts`, `auth.ts`, `account.ts` and `src/env.ts`; UI pieces from `@haruhimemoe/ui` (chips, radios, confirmations, badges, text links, tabs, tables, star ratings, stats, slot badges, action buttons, the header menu, pagination, the visibility picker, `cx`); text formatting from `@haruhimemoe/osu/format`; mod rules (`ratingMods`, `changesStarRating`, `speedRate`), the content filter (`@haruhimemoe/pool/content-filter`) and the packs contract (`@haruhimemoe/pool/service`) from `@haruhimemoe/pool`.
- Files stay under about 250 lines and components under about 200: split by what a part does. No import cycles in `src/`, type-only ones included.
- `utils/` is pure. Server-only modules `import "server-only"`. `src/utils/pack-input.ts`, `fingerprint.ts` and `source-pools.ts` use node:crypto: never import them from client code. Client code never imports the `@haruhimemoe/osu` root (it holds the osu! secret) or `@haruhimemoe/compliance` (its data stays on the server); `tests/unit/tooling/client-imports.test.ts` enforces both.

## 4. File headers

Every `.ts`, `.tsx`, `.mjs`, and `.css` source file starts with:

```ts
/**
 * @file <repo-relative path>
 * @desc <what it is and why>
 * @author David @dvhsh (https://dvh.sh)
 * @created Ddd MMM D, YYYY
 * @modified Ddd MMM D, YYYY
 */
```

Dates match `date "+%a %b %-d, %Y"`. Update `@modified` on edits, never `@created`. Every export gets a doc comment right above it (one line is enough for a constant, type or schema); exported functions, components and route handlers get a JSDoc block with `@function`, `@param`, `@returns` (and `@throws` when they throw). `tests/unit/tooling/jsdoc.test.ts` checks every header and comment.

## 5. Tests

- Everything under `tests/`, mirroring `src/` paths. Write the failing test first.
- `bun run test` runs all three Vitest projects. The unit project runs with `TZ=America/Los_Angeles` on purpose.
- Tests never reach osu!, the mirror, otdb or packs: msw (`setupMsw` from `@haruhimemoe/next-kit/testing`, `onUnhandledRequest: "error"`) with `tests/helpers/{osu,hinai,packs}-server.ts` and `@haruhimemoe/hinai/testing`'s handlers and answers recorded from the mirror, or injected fakes. The fake env is next-kit's `TEST_OSU_APP_ENV` and `stubOsuAppEnv`; the in-memory MongoDB is its `startMemoryMongo` (`tests/setup/integration-global.ts`). Vitest inlines next-kit, so mocks of `next/navigation` reach its components.
- Integration tests use `setupTestDb()` and build rows with `makePool` / `makeMap` (`tests/helpers/records.ts`); admin sessions come from `createTestAdmin()`.
- `scripts/similar/` has its own pytest suite (`cd scripts/similar && uv run pytest`), on tiny fixtures with no network and no database; CI runs it too.
- `tests/integration/e2e/otdb-import.test.ts` runs the importer over the real otdb export only when `POOLS_E2E_EXPORT` names the file; it's skipped otherwise.
- Coverage floor: 90% on `src/utils/**` and `src/schemas/**`.

## 9. Pool data

- The database is always `pools` (`DB_NAME` in `src/lib/db.ts`). `connectDb()` (which also creates the raw indexes and runs the built pools' search-field backfill) reads the user's privileges (`connectionStatus` with `showPrivileges`) and refuses to go on when they reach any other database (`checkDatabasePrivileges` in `src/lib/db-privileges.ts`). It fails closed: an answer that doesn't say who is signed in, or a signed-in user with no privileges listed, is refused too. better-auth and every service go through `connectDb()` first.
- `POOLS_ALLOW_SHARED_DB_USER=true` (exactly `true`, trimmed; anything else is strict) allows a user that reaches other databases, like one shared with packs: the check still refuses the answers above and a user without find, insert, update, remove and createIndex on all of `pools`, and logs one `console.warn` naming the other databases (never the URI). Strict is the default; `.env.example` leaves it empty and a test keeps it that way. SECURITY.md states the risk.
- Server env comes from `src/env.ts` only. `ADMIN_OSU_IDS`, `PACKS_URL`, `POOLS_SERVICE_TOKEN` and `POOLS_ALLOW_SHARED_DB_USER` are read on every call by their own getters. Never print a secret; never read `.env.local` in a tool call.
- Pool ids are `<source>-<id>` for a source pool's first version and `-2`, `-3` for later ones, never reused (`nextPoolId`). An id is also packs' ref for the pool's pack.
- Sources (`src/schemas/pool.ts`, a zod discriminated union on `kind`): otdb keeps its v1 shape `{ kind, id, url, importedAt }`; host and community are `{ kind, id, credit: { name, url? }, importedAt }`, the name 1 to 100 characters once trimmed and through the content filter, the link https only. Leave `credit.url` out when there is none: the driver stores `undefined` as `null`, which fails the schema and drops the pool from every page. `formerSources` entries add `leftAt`. Host and community ids come from `src/utils/source-ids.ts` (a letter, then 7 base36 characters, so they sort after otdb's numeric ids in `bySourceId` and never take a merged record's name). Credit links render with `rel="nofollow ugc noopener"`.
- `tournament`, `round` and `year` hold the effective values: an admin's `edited` value wins, else what `namePartsOf(name)` reads. `tournamentKey`, `searchText` and `sortName` are recomputed with them (`derivedFields`). `visible` is `!hidden && supersededBy === null`, and every public index starts with it.
- The importer (`src/utils/import-plan.ts`) tracks changes per source: a changed source leaves its record (into `formerSources`), a record with no source left is superseded, a new record inherits `hidden`, `badged` and `edited`, a returning fingerprint revives its record. A record takes its name, notes and slots from its lowest source id only when that source is in the run; while it's skipped or missing, the record keeps what it has. The report's superseded and revived lists are net: a record superseded and revived in one run is neither. It never changes `hidden`, `badged` or `edited` on a stored record. Rerunning is safe.
- `/admin/pools/new` (`POST /api/admin/pools`, `src/services/add-pool.ts`) adds a host or community pool through the importer's own `planImport` and writers: maps read by `src/utils/add-pool-input.ts` (a pack key or `/k` link, slot lines, IDs; a `/p/<slug>` link is refused), a new record named `<tournament> <year> <round>` with the typed fields as edits, or the source joins the stored record with the same fingerprint and changes nothing else there (a superseded one is revived). The join is one guarded `$push` (never a `$set` of the sources from a snapshot), a create that meets the fingerprint index is planned again once as a merge, and a source whose kind, credit name and link the record already has adds nothing (`alreadyCredited`). Maps pools never saw get a blank row (`metaSource: "none"`) that the mirror fills at once; `fillMaps` asks for `otdb` and `none` rows.
- Maps carry `usage` (`count`, `lastYear`, `playedAs`, `shown`), rebuilt by `src/services/usage.ts` after every import and every admin change to hidden or year. `count` is distinct current pools; `shown` decides whether `/maps/[id]` exists.
- Hidden pools are invisible on every public surface (search and `/check` within 5 minutes: the CDN keeps their answers that long and nothing can purge them); public pages never read cookies, so `/pools/[id]` 404s them and admins preview at `/admin/pools/[id]`. Superseded pools keep their page with "Replaced by", and are out of search, history, usage, counts, the sitemap and llms.txt; their pack goes unlisted.
- Pack sync: `src/utils/pack-input.ts` builds the pack input and its hash, `src/utils/sync.ts` decides which pools are due (never `gone`; `error` always; `rejected` only when the input changed or on request), `src/lib/packs-client.ts` sorts packs' answers, `src/services/sync.ts` sends at most 5 at a time. 401 and 503 `not_configured` stop a run.
- `bun run import` reads `IMPORT_SOURCES` (otdb) only; host and community pools come in through the admin page. `bun run import otdb [--dry-run] [--file <path>] [--no-sync] [--resync rejected]` (`scripts/import.ts` then `src/lib/import-runner.ts`) runs with the `react-server` condition and writes to the database `MONGODB_URI` names (Bun loads `.env.local`). A real run stores one report in `imports`, even when it throws partway (`ok: false`, with the error). It can't revalidate the site: after an import, Refresh public pages on `/admin` (`POST /api/admin/revalidate`) rebuilds the home page, `/search`, the sitemap, llms.txt, llms-full.txt and every pool and map page. Agents run it only with `--dry-run` unless they're asked to import.
- The home page, sitemap and llms.txt reads (`loadHomeCounts`, `listCurrentPools`, `listListedMaps`, `listPublicBuiltPools`) come back empty only under `SKIP_ENV_VALIDATION`. At runtime a database error throws, so ISR keeps the last good version instead of storing an empty one.

## 10. Search, the check, accounts and admins

- `/search` is ISR (hourly): its server HTML is a default state (`SearchDefault`: the heading, what can be searched, common starts, the latest past pools) that the client `SearchScreen` replaces; results come from `GET /api/search` (CDN cached 5 minutes and never served stale, so a hidden pool leaves search within 5 minutes; 60 requests a minute per IP). Queries are built in `src/utils/search-query.ts`: every one hints the index behind its sort, runs under `maxTimeMS`, matches text as escaped substrings, pages 50 at a time (page at most 200, query at most 100 characters). A new sort needs its index in `src/models` and an explain case in `tests/integration/services/search.test.ts`. No public request runs an aggregation pipeline: public counts use `countMatching` (`src/services/count.ts`, the `count` command), because the driver's `countDocuments` is an aggregation. Admin pages may use `countDocuments`.
- The pools tab has a type (`type=past|built|both`, chips that are native radios, ui's `ChoiceChips`; none or anything else reads as past, so old links mean past pools, and past is never written). Built here (`builtPoolQuery`) lists built pools that are public, not hidden and have maps, on their own indexes (`BUILT_POOL_INDEXES.search*`), with `searchText`, `sortName` and `mapCount` that `toStored` writes with every content change (`src/utils/built-record.ts`; rows written before those fields get them from a backfill that runs once per process at connect, after the indexes, reading only rows with no `searchText` (`src/lib/built-backfill.ts`, guarded writes, errors logged), and reads compute them when missing (`builtSearchFieldsOf`)), each result linking `/pools/<id>` and saying "Built by <owner>". Built pools have no badged or star stats: with either filter set they're left out, and "Built here" hides both rows and clears their values with a note (`BUILT_CLEARED_NOTE`); a `type=built` link reads without them, and its URL drops them. Both lists built pools first, then past pools, each in the chosen order, paging across them. Public built pools with maps are in the sitemap, llms.txt and the home page's Recently built (`listPublicBuiltPools`, `src/services/built-listings.ts`; one made public before its first map isn't listed anywhere, search included); a change to who sees a built pool (visibility, a hide, a delete, an account deletion) calls `revalidateBuiltLists()` so those three rebuild. The home page leads with building (`BUILDER_LINE`, Make a pool to `/new`); past pools are the secondary sections.
- The maps tab has a scope (`scope=all|played`; with none, a link carrying `ar`, `od`, `cs`, `played`, `used`, `last` or `sort` reads as played, anything else as all; a played search always writes `scope=played`, an all-maps search never writes a scope). All maps come from the hinai mirror's search through `src/lib/map-search.ts` (server only, `SERVER_USER_AGENT`, 10 s timeout, 50 a page, zod that drops sets it can't read) and `src/services/all-maps.ts`: disallowed sets are hidden and counted, potential ones say "Check first" (a compact Ranked, Approved or Loved set, as the mirror's own pages send them, is judged with no takedown notice, since it carries none; `/data` says so), unranked ones are tagged, and "played in N pools" comes from one maps lookup. It never calls the osu! API. Anything but a 200 with a list of sets is 503 no-store with the fixed sentence, never an empty page; a 429 or 503 with Retry-After makes the process skip the mirror that long (at most `MIRROR_COOLDOWN_MAX_MS`, a minute) and answer the same 503 meanwhile; a page whose played-in lookup failed is no-store too.
- The map browser (`GET /api/maps/browse`, `src/services/map-browse.ts`, params in `src/utils/browse-params.ts`) searches under a mod lens. Ranked, Loved and Graveyard come from the mirror's mod data (`src/lib/nekoha-search.ts`; its pages start at 1; `sort` is one of `BROWSE_SORTS`, most favourited by default, `pp` being what the mirror does with any other value; a lens that the mirror's pp-maps/stats doesn't list reads as NM, and `src/lib/browse-lenses.ts` keeps that list an hour). Qualified and Pending come from the all-maps search without mods (`modValuesAvailable: false`). Sets are judged as all-maps judges them (`judgeSets`). Stars come from the row, BPM and length from `src/utils/mod-values.ts` (the mirror's rows aren't adjusted), AR, OD and CS from `getModValues` (`src/lib/mod-values.ts`: pp/batch, 100 ids a call, kept 30 days in `mod_values`, where ids the mirror lacked rest 10 minutes and a failed call's ids a minute, as `rest` rows, so a page loaded over and over sends the mirror no call each time); ids it lacks fall back to no-mod values and the math, marked `source: "math"` (the browser says "no mod data" beside them under a mod lens). The pool's own maps (`excludeIds`), played maps (`hidePlayed`) and the BPM, length, AR and OD filters apply to the page after it arrives and are counted. It shares the search's per-IP limit, its CDN caching and the mirror's Retry-After cool-down; a failed mirror search is 503 `browse_unavailable`, no-store. Pool pages read each slot's values under its mods from `slotValues` (`src/services/slot-values.ts`): NM, FM and TB keep no-mod values; HD (the mirror's HD values, as the HD lens shows) and the rest come from `getModValues` or the math (`source: "math"`, "no mod data"). It asks every combo at once under one deadline (`SLOT_VALUES_DEADLINE_MS`, 8 s, well inside `/values`' 30 s `maxDuration`); what hasn't come by then is the math with `complete: false`, and a pp/batch call that times out (or meets the deadline) makes the process skip the mirror for 30 s (`noteMirrorTimeout`, the same cool-down as Retry-After). Past pool pages (`/pools/[id]`, still cookie-free ISR, and the admin preview) read them at render with `pastSlotValues` (each source slot matched to its slot by place, else by map); a built pool's page and its editor read `builtSlotValues` (keyed `<id>:<combo>`, `src/utils/slot-values.ts`), and the editor asks `GET /api/pools/<id>/values` (owner and editors, within `poolOps`) once a slot shows a map and combo it has no values for and nothing is left to save (`src/hooks/useSlotValues.ts`: keys count as asked only after an ok answer, a failure tries again after 2 s doubling to a minute, never after 401, 403 or 404; an answer with `complete: false`, and an editor page read that wasn't complete, shows its math meanwhile and asks again for those keys the same way; a map added mid-request is asked for after it). The Summary's star range per bucket counts only stars under the slot's mods (`source: "mirror"`, or no-mod stars in a no-mod bucket); the rest count as unknown. A render whose mirror call failed shows the math until the next revalidation.
- `/api/check` asks osu! only through `osuBudget` (`src/lib/osu.ts`, next-kit's `createBudget`: 50 calls a minute across instances, 20 per IP; its gate says no for the rest of a request after its first no) and caches beatmapset facts in `setFacts` for 24 hours. A complete answer stays 5 minutes on the CDN, since its map labels and usage come from pools; a partial answer, or one whose maps lookup failed, is never cached.
- Any osu! user can sign in (to make pools); the better-auth hooks refuse nobody and never keep osu! tokens. osu! is a trusted provider for account linking (`requireLocalEmailVerified: false`), so a user row left without its osu! link by a deletion that stopped partway is relinked on the next sign-in; safe because a user row only ever comes from osu! (`<osuId>@osu.local`, no email sign-up). `src/lib/db-indexes.ts` builds (next-kit's `AUTH_INDEX_SPECS` through its `ensureIndexes`) unique indexes on user `osuId`, account `{providerId, accountId}` and session `token`, plus session `userId`; over existing duplicates the unique one is skipped and logged (osu! ids and links named, a session token never) and the rest still build. Admin rights come only from `ADMIN_OSU_IDS`, read on every request: `getUserFromHeaders` returns `isAdmin`, `getAdminFromHeaders` reads a signed-in non-admin (a removed id included) as null. Admin routes answer 404 to everyone but an admin, then refuse other origins (`refuseCrossSite`), then parse a JSON body; admin pages (`requireAdmin`) send a visitor to sign in and 404 a signed-in non-admin. `not_admin` now only names an admin check; `/signin` still explains it. Every sign-in failure lands on `/signin?...&error=<code>` (better-auth's `onAPIError.errorURL` for a callback with no readable state, the button's `errorCallbackURL` with `next` otherwise), and `src/utils/signin-errors.ts` says what each code means. `next` defaults to `/account` and never points at `/signin` itself.
- Public pages still read no cookies (a built pool's page is the exception, below): the header's `AccountMenu` is a client component, and `useAccount` (`src/lib/account.ts`, next-kit's account store) asks for the session only when the readable `pools-signed-in` marker cookie (`SIGNED_IN_COOKIE`) is there (set and cleared by next-kit's `createOsuAuth`, built in `src/lib/auth.ts`; `RestoreSignedIn` on `/signin` and `/account` sets it for a session without one). `/account` shows the osu! account and "Delete my account": the typed-username confirmation lives in the page (no `confirm()`), and `DELETE /api/account` checks the same username (then at most 3 an hour per osu! account), then removes the user's pools (a pool handed to them meanwhile included), sessions, linked accounts and user row (`src/services/account.ts`); a packs outage never blocks it (204, or 200 with `packRemovalsQueued` and a notice).
- Built pools (`built_pools`: `src/models/BuiltPool.ts`, `src/schemas/built-pool.ts`): ids are `b-` and a generated source id, claimed in `built_pool_ids` first so none is ever reused. Slots and buckets are `@haruhimemoe/pool`'s (`poolFields` with its bucket checks), no map twice; nullable fields are stored as null and `buckets` is left out for the default list (`toStored`). Each bucket can have a target (`targets: { [code]: { count 0 to 16, sr?: { min, max } } }`, `src/schemas/built-plan.ts`), set by the `setTarget` op (count 0 with no range clears it), left out when there are none, dropped with its bucket (`tidyPlan`, `src/utils/built-plan-ops.ts`), and copied by Start from this pool; `/new`'s templates (`POOL_TEMPLATES`, `src/constants/targets.ts`) set counts only, never maps. The editor shows placeholders and out-of-range badges, the summary lists both (`src/utils/bucket-targets.ts`), and Find maps puts a bucket's range in the star filter. Each slot can have a note (`slotNotes: { [beatmapId]: text }`, 1 to 280 characters on one line through the content filter), set by `setNote` ("" clears it), keyed by beatmap id so it follows a move, dropped with its map, shown in the editor (`SlotNote`) and on the pool's page (public pools show them). One line means no control characters and no U+2028 or U+2029. Anyone who can't edit the pool sees only notes that pass today's rules and filter (`passingNotes` in `viewOf`), and Start from copies only those, so a note stored before a filter change never shows publicly. Export (`ExportPanel`, `src/utils/pool-export.ts`, on the pool's page and in the editor) is made in the browser from what the page holds: IDs with slot labels, `!mp map <id> 0` then `!mp mods` per slot (osu!'s tournament management commands: `None` for a no-mod slot, which the docs list, rather than leaving the line out, so a room's leftover mods are cleared; forced acronyms space-separated; `Freemod` for FM, TB and freemod slots), and a CSV whose text cells can't start a spreadsheet formula. The owner is a user id; editors are matched by osu! id, so one added by username before their first sign-in gets access when they sign in (the user create hook fills in their `userId`). `version` goes up by one per change; `pack` is the pool's pack on packs (below).

## 11. Similar maps runbook (scripts/similar)

BoBERT (https://github.com/token03/bobert, by token03, MIT; he said we can use the embeddings) publishes `embeddings.parquet` on Hugging Face `token03/bobert` (v14.1: 498,962 osu!standard maps; `beatmap_id` int64, `embedding` fixed_size_list<float16>[384], `density`) and `data/beatmaps.parquet` (`id`, `beatmapset_id` and osu!'s fields). `scripts/similar/` (Python 3.12+, run with [uv](https://docs.astral.sh/uv/): numpy, pyarrow, pymongo; `uv.lock` pins them) downloads both at the pinned revision (`REV` and SHA-256s in `source.py`) into the gitignored `scripts/similar/.cache/<rev>/`, L2-normalizes, and finds each map's top 20 by cosine (`neighbors.py`: batched float32 products on the CPU, a few batches at a time on threads; never the map itself or another difficulty of its set; neighbors at cosine 0.999 or over are copies, reuploads or HP/AR edits in other sets, and are left out). `store.py` writes `{ _id, n, s, rev }` into `similar_maps_next`, then renames it over `similar_maps` (`dropTarget`), so the app never reads a half-written table. The space guard runs before the neighbor math: `dbStats` data + index size now, plus the estimate (a full document's BSON size plus 24 bytes of `_id` index per map, about 80 MB for v14.1), must stay at or under 400 MB, or it refuses. It reads `MONGODB_URI` from the environment, writes to the `pools` database, and never prints the URI. Measured on David's Mac (v14.1, all 498,962 maps, `--out`): the neighbor math took 748 s (about 12.5 minutes) at 3.7 GB peak memory, every map got 20 neighbors, and the import estimate is 80.4 MB. Install uv first if `uv` isn't on the PATH (`brew install uv`).

Only David runs the real import; agents may run `--out` (a local .npz, no database) and the tests, never a write against production. From the repo root:

```sh
cd scripts/similar
uv run --env-file ../../.env.local build.py --dry-run   # prints dbStats and the estimate, writes nothing
uv run --env-file ../../.env.local build.py             # the import (similar_maps_next, then the rename)
uv run build.py --out /tmp/similar.npz                  # neighbors to a local file, no database
```

`--env-file` names whichever env file holds the production `MONGODB_URI`. `--limit N` runs on the first N maps (a trial). Refresh when BoBERT publishes a new revision: bump `REV` and the SHA-256s in `source.py` (the Hugging Face API lists them), run the tests, then the import. The app needs no deploy: it reads `rev` from each row.

- Metadata, robots.txt, the sitemap, JSON-LD and llms.txt all go through `@haruhimemoe/next-kit/seo` with the one `SEO_SITE` (`src/constants/seo.ts`: home keyword "osu! tournament mappool builder", `SITE.description` at 160 characters or fewer, the static `opengraph-image.png` at its real 1200x630, `HARUHIME_ORG`, haruhime.moe as parent).
